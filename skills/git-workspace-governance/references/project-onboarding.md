# 把规范入口挂进项目（需人类授权）

本 skill 是被动加载的：agent 只有在合适的时机想起它，才会用到它。跨 session、换模型或长任务进行中，约定很容易被忘记。把入口登记到项目每轮都会读取的 instructions 文件，比依赖聊天记忆可靠。

## 1. 边界：建议 ≠ 授权

- `AGENTS.md`、`CLAUDE.md`、`.cursorrules` 等 instructions 文件是**项目长期准则**，属于人类所有；
- agent 只能**提出建议、给出草案**，不得擅自编辑；
- 取得用户明确授权后，再通过项目正常的 PR/审查流程修改；
- 没有授权时，只在回答里建议，不在仓库里留下任何改动。

## 2. 什么时候提这个建议

- 接手项目时发现 instructions 文件里没有工作区治理入口；
- 项目有多个 session / agent / 宿主机共用仓库，却只靠口头约定；
- 项目刚引入本 skill，还没有登记入口；
- 发现 agent 反复遗忘 canonical/worktree/清理/发布边界（正是登记入口要解决的问题）。

## 3. 授权话术（示例）

> 我注意到仓库里没有登记工作区治理入口，跨 session 时 agent 容易忘记 canonical/worktree/清理/发布边界。
> 建议在 `AGENTS.md` 增加 2–4 行入口（草案如下），**是否修改由你决定**；同意后我按项目 PR 流程提交。
> 我不会擅自改 `AGENTS.md`。

## 4. 按项目形态写

### 有 AGENTS.md（推荐）

在文件靠前位置加 2–4 行：

```markdown
- 仓库级工作区治理（canonical checkout / task worktree / 清理备份 / 发布 SHA）：
  使用 skill `git-workspace-governance`；接手、清理或发布核对前先运行其只读体检。
- 修改本文件需要人类确认；项目规范优先于 skill 的缺省框架。
```

### 使用其它 instructions 文件

`CLAUDE.md`、`.cursorrules`、`GEMINI.md` 等是项目已有约定的一部分：**项目文件优先**，把入口加在项目实际使用的那一份，不新增并行文件。

### 没有 instructions 文件

先建议用户创建并决定位置与内容；不要为了方便 agent 而擅自往仓库根目录放文件。

## 5. 登记内容原则

- **只放入口和边界**：skill 名 + 最关键的 1–2 条规则 + 体检命令；
- **不要整份复制** skill 正文：会造成重复、内容漂移、上下文膨胀；
- **不要写成强制依赖**：项目没安装该 skill 时仍应可工作，入口只是提醒；
- 可以附上只读体检命令，例如 `python3 .../check_workspace_state.py --repo .`，但以项目实际路径为准；
- 若项目同时使用配套 skill（如 `long-running-project-harness`），入口可并列提及，不改变各自职责。

## 6. 修改流程

1. 用户授权具体文件与草案；
2. 在项目自己的任务分支上修改（遵循项目的分支/PR 规则），不直推集成分支；
3. 独立审查/CI 通过后合入；
4. 报告实际改了什么、由谁授权。

## 7. 验证与常见错误

验证：新开 session 读取 instructions 文件，确认能看到入口、skill 名称正确、且项目没装 skill 时入口仍不阻塞工作。

| 错误 | 后果 |
|---|---|
| agent 未经确认直接改 `AGENTS.md` | 越权修改项目准则，人类无法掌控 |
| 把整份 skill 内容贴进 `AGENTS.md` | 重复、漂移、上下文膨胀，后续维护两套 |
| 入口指向未安装的 skill 且写成强制要求 | 其他 agent/机器上直接失败 |
| 在没有 instructions 文件的仓库里擅自新建 | 违反项目布局，可能被误当规范 |
| 把入口写成"必须使用某工具" | 剥夺项目自有流程的选择权 |

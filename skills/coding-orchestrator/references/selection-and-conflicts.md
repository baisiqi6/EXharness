# 选择方法与处理冲突

先看用户要求和项目既有规范，再看当前缺什么。明确的小改动直接完成；只有选择不明或要求冲突时，才需要比较方法。

## 当前需要与最小做法

| 需要 | 没有专项包时也可执行的做法 |
| --- | --- |
| 目标或方案不清 | 读取必要事实，列出会改变结果的关键问题与少量方案；等待决定的分支先停，其余独立工作继续。 |
| 规格容易产生不同理解 | 在已有规格或计划中明确输入输出、边界和验收例子，再实现对应行为。 |
| 用户/项目要求 TDD，或需要以测试先定义行为 | 先运行行为测试，确认因待实现行为失败，再最小实现、运行通过，按需重构并复测。 |
| 已出现异常 | 根据证据复现或缩小范围，验证假设，再修复原失败行为并检查相邻兼容。 |
| 需要结构取舍 | 从直接方案开始；有实际变体、难改分支或已声明的结构需求时再比较小型抽象，用验收检查其收益。 |
| 需要审查 | 沿实际入口核对目标、差异与证据，区分阻塞问题和可选建议，给出有依据的结论。 |

可按进展切换方法，不要求依次执行上表。选择某套完整工作流时，核对其实际步骤和产物；不能删掉关键步骤后仍声称完整遵循。

## 只处理已经出现的冲突

- **默认位置不同**：查明项目正式 locator，保留原生规范/设计/执行产物的职责。必要时由项目明确采用原生文件作为权威，链接已有材料，不双写同一用途的计划。
- **范围或抽象扩大**：核对建议解决的具体问题、现有实现及验收需求。保留能解决问题的最小改动；审查中的额外清理单列为可选，不静默纳入实现。
- **验证强度不同**：用户/项目明确要求的测试或审查继续执行；其余验证与行为变化和实际影响相称。测试未运行、失败或工具不可用时如实说明。
- **多套流程都声称主导**：查明客户端实际自动注入、项目选择和当前活动阶段。普通接入说明不能关闭钩子或覆盖上层指令；无法同时满足时报告具体冲突，等待有权决定的一方选择。

补充规范时使用[同一接入记录](convention-profile.md)，保存已知矛盾及其处理依据即可；无需为尚未组合的所有规范预建兼容结论。

# 发布前核对

合并、发布和业务验收是三件不同的事。发布前用只读命令读回四个 SHA，不要用本地目录内容或对话记忆代替。

## 1. 四个 SHA

| # | 事实 | 读法 |
|---|---|---|
| 1 | 任务被合入的提交 | PR / 合并记录里的 merge commit 或 squash commit SHA |
| 2 | 本地集成分支 | `git rev-parse <integration>`（在 canonical checkout 或任意 worktree） |
| 3 | 远程集成分支 | `git ls-remote <remote> refs/heads/<integration>`（或先 fetch 再 `git rev-parse <remote>/<integration>`） |
| 4 | 生产 / 已部署 HEAD | 在部署目标上执行 `git rev-parse HEAD`，或读取发布记录中的 SHA |

四个值分别读回、分别记录；任何两个“应该一样”都不构成省略核对的理由。

## 2. 发布判定

- 待发布 SHA 必须是已审查并记录在案的提交；
- 生产只快进到该 SHA；不做历史改写；
- 本地集成分支或远程集成分支比目标 SHA 多出的提交不自动发布，需要另外审查；
- 发布快照用 tag 或固定 SHA 的只读 checkout，避免“发布时工作区刚好是什么”这种不确定性。

## 3. 流程

1. 读回四个 SHA，记录到发布记录；
2. 确认待发布 SHA 是生产当前 HEAD 的后代（快进关系）；
3. 在 release snapshot 或部署目标上执行发布，按项目手册；
4. 发布后再次读回生产 HEAD，与目标 SHA 比对；
5. 报告：实际发布 SHA、生产新 HEAD、上一版 SHA（回滚锚点）、验证结果。

## 4. 边界

- 工作区清理、worktree 退役、分支删除都**不**等于发布，也不授权发布；
- 合并 **不** 等于部署，部署 **不** 等于真实业务验收；
- 不要把“CI 通过”“PR 已合并”“本地测试通过”写成“已发布”。

## 5. 回滚锚点

发布前记录当前生产 HEAD 与回滚方式；回滚同样按项目手册和用户授权执行，不临时改写共享历史。

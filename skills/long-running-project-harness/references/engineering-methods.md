# 按需选择工程方法

方法尚未确定、缺少所选专项 skill，或方法流程与项目约定冲突时读取。用户要求和项目已有规范
决定必须遵循的做法；其余按当前任务选择最小够用的方法。目标、做法和验证已经清楚的小任务
直接执行，无需先经过完整的方法选择流程。

## 根据当前需要选择

| 当前需要 | 最小做法 |
| --- | --- |
| 直接实现：目标明确、局部改动 | 找到实际入口，做必要修改，运行相称的现有测试或直接检查。 |
| 澄清与头脑风暴：目标、约束或方案未定 | 梳理关键歧义，比较少量可行方案；依赖用户决定的部分先确认，其余独立工作继续。 |
| 规格驱动（SDD）：接口或业务规则容易产生不同理解 | 在项目已有规格或任务计划中明确输入输出、边界与验收例子，再据此实现和验证。 |
| 测试驱动（TDD）：用户/项目要求，或当前行为适合用测试先定义 | 先写行为测试，运行并确认因待实现行为而失败，再做最小实现使其通过，按需重构并复测。 |
| 调试：出现异常，根因尚未核实 | 核对实际证据，复现或缩小问题，验证假设后做最小修复，再检查原失败行为。 |
| 审查：已有方案或改动需要独立判断 | 按[审查策略](reviewer-strategy.md)核对目标、实际入口、差异和验证证据，给出有依据的结论。 |

这些是当前动作，不是新的风险模式或生命周期。一个任务可以先澄清、再明确规格、实现、验证
和审查；按实际进展选下一步，不机械执行每一行。模型自身能力和当前工具可影响具体做法，
用户/项目明确要求及实际验收标准保持有效。

## 按需使用专项能力

已安装的专项 skill 可以提供更深入的方法，只读取当前动作需要的内容；未安装时使用上表的
简短做法，不因缺少某个方法包要求安装整套工具。可选实现见[主入口](../SKILL.md#可选集成非依赖)。
实际工具或权限缺失时仍按[执行边界](workflow.md)报告具体缺口，不把方法 fallback 当作已有能力。

## 处理实际冲突

- 方法的默认文件位置与项目不同：沿用[已登记的任务记录](storage-and-recovery.md#从任务节点接续)，将结果写回原计划或链接项目已有材料。
- 方法建议的抽象或额外步骤超出当前需要：先核对具体问题、适用条件和已有能力；按[实现纪律](workflow.md#实现纪律)保留满足目标的最小改动与相称验证。
- 明确要求之间无法同时满足：说明具体冲突及影响，交由有权决定的一方裁定；EXharness 的方法参考不改变指令优先级或项目授权。

方法选择已清楚时无需额外登记；需要解释取舍或交接时，在已有任务记录中简短说明依据。
